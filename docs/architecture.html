Forge Architecture

Forge is a Kubernetes operator that manages ZarfPackageJob and UDSBundleJob custom resources. It validates, builds, monitors, and chains Kubernetes Jobs to execute package operations (Build/Create → Publish → Deploy) and reports results back to the CRD status.

Go Generics Kubernetes Operator k8s.io/api v0.36 OpenTelemetry Helm Chart
🗺

Overview

Forge runs two processes: a Controller that reconciles CRDs and manages Job lifecycles, and a Webhook Server that validates admission requests against ServiceAccount permission annotations. Both are deployed as Kubernetes Deployments in forge-system.

Entrypoints
  • cmd/controller/main.go — Operator controller
  • cmd/webhook/main.go — Admission webhook (TLS :8443)
  • cmd/kubectl-forge/ — kubectl debug plugin
CRD Types
  • ZarfPackageJob — Build / Publish / Deploy Zarf packages
  • UDSBundleJob — Create / Publish / Deploy UDS bundles
  • API group: forge.dev/v1alpha3
Action Chains
  • Build / Create
  • Publish
  • Deploy
  • BuildPublish, BuildPublishDeploy
  • PublishDeploy
Observability
  • OpenTelemetry metrics + tracing
  • Prometheus scrape at :8080/metrics
  • Structured logging with correlation IDs
  • Health: :8081/healthz & /readyz

Key Concepts

Go Generics
  • GenericController[T] works for both Zarf and UDS
  • GenericJobMonitor[T] shared monitoring loop
  • ActionHandler[T] typed handler interface
  • Eliminates duplication between Zarf/UDS paths
JobBuilder Pattern
  • Fluent API building batchv1.Job specs
  • Manages init containers for source retrieval
  • Enforces non-root security contexts
  • Handles all volume wiring automatically
Annotation RBAC
  • ServiceAccount annotations define per-user capabilities
  • Glob pattern matching on repos, registries, buckets
  • Webhook validates on every CREATE / UPDATE
  • No cluster-wide RBAC needed for individual devs
Action Chaining
  • Artifact PVC persists between steps in a chain
  • Monitor triggers next action on Job success
  • Each step is an independent K8s Job
  • Failure stops the chain and marks CRD Failed

Webhook Permission Model

The webhook server validates every CREATE / UPDATE against the submitting ServiceAccount's forge.dev/* annotations. All checks must pass or the request is denied.

How it works: Admins annotate ServiceAccounts with glob patterns describing what each identity is allowed to do. The webhook enforces these rules at admission time — no cluster-level RBAC changes are needed per developer.

Source & Destination Plugins

Sources produce init containers that pull package code into /workspace. Destinations configure the publish command and any required credential volumes/env vars.

Sources (pkg/sources)
  • GitSource — SSH key, token/password, OAuth, custom hosts
  • S3Source — AWS IAM EnvVar/File/Node, MinIO, custom endpoint
  • OCISource — Registry credentials, skopeo pull
  • LocalSource — hostPath mount (dev mode only)
Destinations (pkg/destinations)
  • S3Destination — publish oci://s3://…, AWS creds EnvVar/File/Node
  • OCIDestination — publish oci://registry/…, Docker config secret
  • LocalDestination — publish tarball://…, ephemeral storage
